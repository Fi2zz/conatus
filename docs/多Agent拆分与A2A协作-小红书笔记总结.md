## 一、什么时候该拆 Agent

原文给出的信号很具体——单个 Agent 开始失控：

- 工具挂到 **30 个**；
- Prompt 写到 **2000 字**；
- **路由错误率飙升**。

出现这些症状，说明"一个 Agent 包打天下"已经到边界，该拆了。

拆分的判断依据仍是那句话：**"路径是否可预知"**（原文承接其上一期内容，本篇未再展开）。

## 二、典型拆法：金融客服

原文用金融客服做样板，拆成"一个分诊台 + 若干专职工"：

| 角色 | 职责 | 工具规模 |
|---|---|---|
| **前台 Agent** | 意图识别 + 分诊（分类器 + 路由表） | 极少 |
| **账单 Agent** | 账单查询 / 还款 / 分期 | 账单 API × 5 |
| **理赔 Agent** | 保单查询 / 理赔进度 | 理赔 API × 6 |
| **兜底** | 拿不准就转人工，别硬撑（合规要求） | — |

效果：**每个 Agent 工具少、Prompt 短、职责单一，出错率立刻下来**。

注意"兜底转人工"在原文里是并列的一等公民，而不是异常分支——金融场景下它由合规要求驱动。

## 三、拆完之后：Agent 之间怎么协作

核心问题从"怎么写好一个 Prompt"变成"多个 Agent 怎么对话"，对应 **A2A（Agent-to-Agent）协议**：

- **统一的任务委派格式**：任务描述、状态回传、结果结构标准化；
- **可外包 + 可跟踪**：一个 Agent 能把子任务外包给另一个，并跟踪其进度；
- **与 MCP 互补**：**MCP 管"Agent 怎么用工具"，A2A 管"Agent 怎么找 Agent"**。

## 四、三种协作模式（按复杂度递进）

| 模式 | 形态 | 适用 | 原文评价 |
|---|---|---|---|
| **路由模式** | 前台分诊，一次转发 | 覆盖约 **80%** 场景 | 起步首选 |
| **流水线模式** | A 的输出即 B 的输入 | 如质检 Agent 审客服 Agent 的话术 | 顺序依赖明确时最划算 |
| **协商模式** | 多 Agent 围绕任务动态协作 | 任务边界本身不确定 | **慎用**：成本和延迟都会翻倍 |

## 五、经验法则

> 从路由模式起步，能单 Agent 就别 Multi-Agent——**每多一个协作节点，可观测和调试成本都是乘法**。

这也是全篇的落脚点：Multi-Agent 不是能力升级，而是一次**用运维复杂度换职责清晰度**的交易，只有当单 Agent 的失控症状真实出现时才值得付账。


## 七、一句话概括

单 Agent 出现"30 个工具 / 2000 字 Prompt / 路由错乱"时就该按职责拆；拆完用 A2A 标准化委派，协作模式从路由起步，**能用单 Agent 就别上 Multi-Agent**。

## 附：与 conatus 的对照（非笔记原文）

- **"路径是否可预知"= 是否该分叉成子 Agent**，与 `conatus_agent` 的 sub-agent 划分思路一致：确定性的编排留在主循环，不确定的探索才下放。
- **路由 / 流水线 / 协商**三档，在 conatus 里分别对应：`conatus_intent`（意图路由）、`conatus_workflow`（流程编排）、`conatus_team`（多智能体协作，实验性）。
- **"每个协作节点成本翻倍"**恰是 conatus 用 `Context` 父子树 + `conatus_tasks` 任务树来对冲的部分——节点是一等结构，释放即级联回滚，可观测性不靠外挂。
- **A2A 与 MCP 分工**：`conatus_mcp` 已覆盖后者（"Agent 怎么用工具"），前者尚无对应包，属于潜在空白。
