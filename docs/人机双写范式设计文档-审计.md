## 总体判断

作为设计随笔，它的问题意识、原语映射与架构分层是扎实的——`effect scope = 补丁` 的映射确实
近乎天然，§6.1「机制层不可被会话改动」是全篇最有价值的承重墙。但文档头部标注「未实现」的同时，
正文多处用**现在时断言尚未存在的行为**，并有三处**事实错位**。这恰好是它最看重的「诚实性」
承诺最该守住的地方。

严重度约定：**A = 事实错误（已核对，须改）**；**B = 内部矛盾 / 逻辑**；**C = 覆盖缺口**；
**D = 值得保留（勿因精简而删）**。

## A. 事实错误（已核对，必须改）

### A1. §1（第 23 行）「三个作者（人、AI）」——数量自相矛盾
括号里只列了两个主体。应为「两个作者」，或补出第三个（若指「文档 / 故事」，那不是作者）。
§9 一页总结也只写「人机」。

### A2. §4.7（第 171 行）「fs 插件已有 git 能力」——归属错误
`fs` 是能力缝（`packages/conatus_foundation/lib/src/fs.dart`），只有 `resolve` / `readText` /
`editText` 等文件原语，**没有任何 git 方法**。git 能力实际在 `conatus_code`：

- 只读工具 `git_status` / `git_diff` / `git_commit` 在
  `packages/conatus_code/lib/src/tools/git_tools.dart`；写工具 `git_add` / `git_branch` /
  `git_stash` 在 `packages/conatus_code/lib/src/tools/git_write_tools.dart`——读写分文件，
  与风险分级对应；
- 更贴题的是检查点子系统的**影子 git 仓库后端**：
  `packages/conatus_code/lib/src/checkpoint/checkpoint_store_git.dart`。

应改指 `conatus_code`。

### A3. §4.7（第 171 行）「git 是成品答案，不重造」——与仓库已落地的决策冲突
`conatus_code` 的检查点恰恰是**两套后端并存**：

- 自研 gzip 归档（`checkpoint/checkpoint_store_archive.dart`），注释自陈
  「零外部依赖，任何环境可跑；代价是同一文件每个版本各存完整内容」；
- 影子 git 仓库（`checkpoint/checkpoint_store_git.dart`）。

即项目已经选择「部分重造」。文档要么承认这条既成取舍、说明为何工作区级回溯仍建议纯 git，
要么把主张降级为提案。

### A4. §4.6 / §4.7 忽略了已实现的工作区级检查点机制
`conatus_code` 的 checkpoint 已提供：turn 0 基线 + 每轮差量、keep-N 保留、rsync 恢复语义、
符号链接 fail-closed，以及**每份快照随存 `lastEventId` 关联 session fork 切点**
（见 `checkpoint/checkpoint_store.dart` 的 `snapshot(..., {lastEventId})` 与
`checkpoint/checkpoint_restore.dart`）。

这已经是 §4.6「检查点」和 §4.7「哪个 commit 对应哪段故事」在**工作区层**的落地。文档把它们
当作待建提案，会让读者误判起点。建议改写为「现有 checkpoint 已覆盖工作区层，本文档补的是
**文档内**粒度」。

### A5. §5（第 199 行）「system-prompt 插件每轮把最终上下文写进 session-log」——现在时断言未实现，且与 §7.1 自相矛盾
`packages/conatus_foundation/lib/src/system_prompt.dart` 只是段/上下文的注册表 + `assemble` /
`render`，无任何 session-log 写入。§7.1 表格（第 241 行）自己也写「**需增加**每轮写 log 补丁」。
§5 应改成提案语气。

### A6. §2.5 / §7.1「模型可见性不变量」——并非现有不变式
该词全仓只出现在本文档内。session-log 的实际硬不变式是**「只追加」**
（`packages/conatus_foundation/lib/src/session_log.dart:5`）；
「可见性」在仓库里只指技能过滤（`packages/conatus_skill/README.md:116`）。
要么明确「这是本范式**新引入**的不变式」，要么删掉「现有」。

### A7. §7.1（第 241 行）context-cache 功能失准
`context-cache`（`packages/conatus_agent/lib/src/caching.dart`）是**前缀指纹 + 命中遥测**，
服务于服务端 prompt 缓存，不是「每轮上下文装配增量的存取」。复用其**思路**没问题，但表格
把它写成了现职。

### A8. §2.3（第 66 行）「复用 `tool_result_eviction` / layered compaction」——机制不对口
`tool-result-eviction`（`packages/conatus_agent/lib/src/tool_result_eviction.dart`）按阈值把
**超长工具结果**落盘；`layered-compaction` 按类别折叠**较早事件**。两者都不是「thinking 专属
的 transient 驱逐」。应降为「类比这两个模式」。
同一不对口在 §7.1 映射表「layered compaction / tool_result_eviction → 检查点 / transient
驱逐」一行再次出现，修复时需两处同改。

### A9. §4.6 / §5「完整视图靠 fold」依赖的路径尚不存在
`packages/conatus_compaction/README.md`「限制」明确写道：**「滚动摘要本身还没有『从日志折叠
重建』的通路，fork 或重开进程后需要重新压缩」**。文档把「增量落 log、完整视图靠 fold」当成
已解决的闭环，实为一个真实缺口。

### A10. `conatus_viva` 引用——内容准确，但不可解析
「`state.json` + 步级幂等 + artifacts 落盘 + dry-run」经核对**属实**：兄弟仓库
`../conatus_viva` 的 `README.md` 确有 `state.json`（`state.dart`：原子写、任务恢复、成本核算）、
`orchestrator.dart`「步级幂等 + dry-run 停点」、`pipeline_out/` 产物落盘、断点续跑。
但它不是本仓内容，读者在 HEAD 处无法解析——补路径或链接。
`Cordis`（第 47 行）同理：根 `README.md:1802` 有官方链接（`cordiverse/cordis`），文档应引一次。

## B. 内部矛盾 / 逻辑

### B1.（关键）§2.1 公式 `state(t) = fold(patches[0..t])` 与 §4.4「只追加 + supersede」不自洽
若存储只追加，supersede 补丁的序号 `j > t`；则对任意 `i < t < j`，`fold([0..t])` 仍折叠到
**旧的**补丁——「修改补丁」不会追溯影响较早的时刻，与「改状态是修改区间里的补丁」直接冲突。
「在序列原位置登记 supersede」的写法见第 143 行（§4.4），与公式同出一处冲突。

需要说清：supersede 是**逻辑生效视图**，`state(t)` 折叠的是「截至 t 生效的补丁集」，而非字面
`patches[0..t]`。否则全篇的数学招牌是错的（这是唯一一处写法与存储规则打架的地方）。

### B2. §2.3（第 66 行）「成本为零」vs §5（第 197 行）「每轮完整上下文进 log 会膨胀」——直接打架
§2.3 的「零成本」本意是「thinking 不进文档」，但写成无修饰断言后被 §5 自我否决。加限定语。

### B3. §5 与 §6.1 的次序
§6.1「机制层不可被会话补丁改动」是防止「一个补丁改掉 log 只追加」的承重墙；但 §5 先出现
「system prompt 自己也是补丁……直接在历史里改」，读者到 §5 时会觉得自相矛盾。
**把 §6.1 的墙提前声明**，再在 §5 写明「可行仅因 system-prompt ∈ 策略层」。

### B4. §4.2 可逆性分类 × §4.4 supersede 的交互未定义
一个已经触发「单向门」效应的补丁，被 supersede 意味着什么？§4.3 用「线性化」回避了，但
supersede 与**已提交副作用**的关系没写。属于真实语义空洞。

## C. 覆盖缺口（值得补）

- **补丁授权边界**：给了「作者」，没给「权限」——谁能 supersede 谁的补丁（人 vs AI 的身份
  是否构成授权墙？）。这是「机制层」应守的一条。
- **多用户 / 多设备**：CRDT 只作为「并发第三档」，未触及分发 / 冲突。
- **§6.3 预设供应链**：只提了一句白名单 / 风险分级，却正好是 §6.1 那面墙的延伸——值得独立成节。
- **`文档快照` 与 `完整上下文装配`（§3 vs §5）未统一**：两处描述「模型看到什么」的口径不同，
  读者要自己对齐。

## D. 值得保留（勿因精简而删）

- §2.2 四操作统一表（生成 / 接受 / 拒绝 / 直接改）——全篇最好的抽象。
- §4.1 checkout 而非 re-execution——正确且重要。
- §4.3 单向门 + §4.8 / §7.3 显式非目标（分支不做自动合并等）——诚实收边。
- §6.1 机制层 ≠ 预设——与仓库实际的「装配模式（机制）/ skill markdown（预设）」完全同构，
  是文档最有前途的架构主张。
